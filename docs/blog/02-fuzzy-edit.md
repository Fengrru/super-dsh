# 为什么我给 fuzzy edit 加了五道护栏

> 容错匹配本身不难；难的是在“容忍差异”之后，仍然能证明改的是正确的那一段。

## 一个模型很常见的错误

Agent 读到一个函数，记住大概长这样：

```ts
function clamp(value, min, max) {
  return Math.max(min, Math.min(max, value))
}
```

但文件里实际是 CRLF、两个空格的缩进，或者参数之间多了一个空格。dsh 的 `edit` 要求 `old_string` 精确匹配并且唯一；差一个字符就拒绝。模型于是重试、换一段、再失败，任务被一个和推理无关的格式问题拖住。

一个自然的想法是：既然差异只是空白，那就做个“宽松匹配”吧。

问题在于，宽松匹配很容易变成“看起来改了，其实改错了”。错改不可恢复，漏改可以重试。所以 `fuzzy_edit` 的设计目标不是最大化命中率，而是：

> 在安全的前提下尽量命中；不能证明安全时，宁可拒绝。

## 8 种策略，但先精确匹配

`fuzzy_edit` 是一个 fallback 工具，不是替代 `edit`。它先走字面匹配；失败后才尝试 8 种容错策略，包括空白归一化、缩进归一化、行尾归一化、Token 序列匹配、Levenshtein 兜底等。

找到候选区域后，它不会直接把旧字符串替换成新字符串，而是：

1. 用候选区域的**精确字节**作为 `old_string`；
2. 调用 dsh 的 `ctx.fs.editText`；
3. 保留 dsh 的原子写、先读后写、沙箱策略和唯一匹配检查。

这一步很关键：容错只发生在“定位”，实际写入仍然走 dsh 的受控编辑路径。插件没有绕过宿主的写文件策略。

## 五道护栏

### 1. 匹配字节必须唯一

候选区域在文件中只能出现一次。如果同一段文本出现两次，即使两个都“看起来像”，也拒绝。歧义不是靠相似度解决的。

### 2. 首尾锚点必须一致

匹配区域的第一个非空行和最后一个非空行，必须分别对应请求的第一/最后一个非空锚点。这样不会因为中间某段相似，就把相邻函数一起吞掉。

### 3. Token 多重集相似度 ≥98%

把旧字符串和匹配区域切成标识符/Token，比较多重集相似度。低于 98% 拒绝；只有专门的 typo 策略允许 90%。这不是语义相似度，而是一个保守的“它们是否是同一段代码”的检查。

### 4. 覆盖至少一半请求非空行

匹配区域必须覆盖请求中至少一半的非空行。防止只匹配到一小段公共前缀就误判为完整匹配。

### 5. 大小上限与边界修剪

请求和匹配区域有大小上限；如果匹配区域比请求多出的是纯空白，可以修剪边界；如果多出的是实质代码，拒绝。边界越界不是“多改一点没关系”，而是可能的错区编辑。

这五道护栏不是装饰。它们的存在让 `fuzzy_edit` 可以接受“漏掉一些本来能修的情况”，但不能接受“改错一次”。

## 80 个案例的实验

我们构造了 12 个真实模板（TypeScript、Python、Rust、Go、CSS、YAML、SQL、Markdown、shell、React、Java），每个模板做 6 种变化：

- 精确；
- 空格漂移；
- 缩进漂移；
- 行尾 CRLF/LF 漂移；
- Token 间距漂移；
- 空行漂移。

再加 8 个对照：4 个歧义重复块、4 个完全无匹配请求。总计 80 个案例。

| 指标 | dsh `edit`（精确） | `fuzzy_edit` |
|---|---:|---:|
| 正确（80） | 27（33.8%） | **72（90.0%）** |
| 可应用案例中实际应用（72） | 19（26.4%） | **64（88.9%）** |
| 错区编辑 | 0 | **0** |
| 对照正确拒绝（8） | 8（100%） | **8（100%）** |
| 中位延迟 | 0.004 ms | 0.6 ms |
| p95 延迟 | 0.03 ms | 14.5 ms |

分类型看，空格漂移 5→11，缩进 0→11，行尾 0→11，Token 间距 2→9，空行漂移 0→10，精确匹配保持 12→12。

8 个原本会失败的案例被安全拒绝，而不是被悄悄改错。这是设计目标的一部分。

## 为什么不做 replace_all

`replace_all` 看起来是自然的下一步：既然能模糊匹配一个区域，为什么不能匹配多个？

因为证明“每一个匹配都是用户想要的位置”比证明一个匹配难得多。多个候选区域之间可能互相重叠，可能有歧义，可能一个改对、一个改错。错改不可恢复，批量错改更不可恢复。

所以 `fuzzy_edit` 故意只处理单区域。需要批量替换时，用 dsh 的精确 `edit` + `replace_all`，前提是文本确实精确。

## 这个实验没有证明什么

它证明的是：在“格式漂移”这个受控语料上，容错匹配能显著提高正确率，同时不引入错区编辑；它没有证明：

- 真实会话里格式漂移的出现频率；
- 在超长文件、压缩单行代码上的召回；
- 多种漂移叠加时的稳定性；
- 模糊匹配对模型行为的长期影响。

因此它默认开启，但每次调用仍然有大小上限和拒绝路径。它的价值不是“永不失败”，而是“失败时更安全”。

## 小结

`fuzzy_edit` 的核心不是那 8 种策略，而是策略之后的五道护栏，以及“漏改优于错改”的排序。
